# PokéVerse 長期自動化 — AI 工作規格

專案：https://github.com/borago0219-chatgpt/pokemon-universe-pokedex

## 目標與範圍
非官方粉絲圖鑑：「跨作品寶可夢知識庫 + AI 生圖圖鑑 + 長期更新系統」。
**程式碼已公開不代表網站已發布；未經使用者同意，不自行部署、發布待審內容、付費或放寬權利審查。**

## 主流程的唯一編號與每日鎖定
1. 主流程從全國圖鑑 **#001 妙蛙種子** 開始，此後只按全國圖鑑號碼 +1 遞增，絕不跳號。既有 #025 皮卡丘、#133 伊布等舊草稿和圖片保留作歷史成果或後續回補，不能當作跳過 #001～#024 的理由。
2. 建設（20:00）、生圖（21:00）與獨立審核（22:00）三個排程共用 `automation/progress.json.daily_focus`，均使用台灣日期 `Asia/Taipei` 與**同一個** `national_id`。每天最多處理一隻；不依 queue 首項、image_queue 首項、現有 pokemon.json 編號或熱門程度另選別隻。
3. 建設任務是每日焦點的唯一設定者；每天先檢查昨日焦點和 `reviews/` 審核報告。如上隻有任何必需項目未完成，將同一 national_id 延續到今天，更新 `date` 和缺漏；額度、時間、查證、生圖、頁面接線或審核受阻也一樣。當日若提早完成，停止，不啟動下一隻。只有到**下一個台灣日曆日**且已核實上一隻全部完成時，才能設為上一編號 +1。
4. 即使 `data/pokemon.json` 尚無下一編號，也不可跳號；基本資料由 GitHub Actions 專管，建設任務可在 `data/guides.json` 保存獨立且可核實的研究，並將基本資料缺漏記入 `daily_focus.missing_sections`。不能修改 `data/pokemon.json` 或 GitHub Actions。
5. 先前 queue/image_queue 保留供追溯和同編號重用；與今日焦點不同的 pending 任務不執行、不自動補貨來湊數。版本更新需要修訂舊編號時，只登記 `update_backfill` 待辦並標明來源、日期、原因，不能破壞主流程順序或在同一天執行第二隻。

## 完成門檻（全部通過才能換號）
- 基本資料及必要的型態、進化等資訊有可核實來源。
- 各代主機遊戲出現方式已核對；不出現、轉入、限定活動與未知明確區分。
- 各版本捕捉／取得方法與條件已核對。
- 按適用版本及玩法提供合法、可核對的推薦配招。
- Pokémon GO 的取得方式、可學招式、PvE/PvP 等用途已核對，歷史活動不冒充現況。
- 至少一張此編號**實際生成並保存**的圖片，含真實格式、來源與 metadata；提示詞／占位符不算。
- 網頁圖鑑在可核實的私人預覽中正確顯示該編號的資料與合規可展示圖片。未通過權利或展示審核的候選圖不能擅自作公開網站素材；必要時保持缺漏，不假稱完成。
- **當日獨立審核**有完整報告且無 critical/high 重大缺漏；確認的是本角色全部必需項目，而非僅一兩篇攻略。無法核對的項目不能算完成。

`daily_focus` 至少記錄 `date`、`national_id`、名稱、`completed`、研究/圖片/預覽/審核狀態、`missing_sections`、來源查核日期、交接狀態。核實「不適用」可標 N/A；未知或缺證據仍是缺漏。公開發布與候選內容完成分開記錄；不可用未發布冒充網頁預覽成功，也不可因程式碼存於 GitHub 就認定網站已正確顯示。

## 三個排程的交接
1. **20:00 建設**：讀最新版 README、progress、guides、pokemon、圖片紀錄、網站程式與 reviews/ 最新報告；鎖定或沿用唯一焦點，研究並保存可核實的部分，更新 `daily_focus.missing_sections`、`handoff.construction` 和同編號 image_queue，留下來源和本次提交。每日不限同一寶可夢的指南主題數，但**不得處理第二個 national_id**。
2. **21:00 生圖**：只讀當日 `daily_focus.national_id`；沒有焦點或前階段未保存就等待。只查同編號圖片；已有合格實圖重用，缺圖才依既有 Leonardo.Ai 免費額度及雲端規則生成最多一張。核對格式、metadata、GitHub 內容後安全更新同編號 image_queue、`daily_focus.image_status` 及 `handoff.image`。不改焦點或攻略。
3. **22:00 審核**：只審當日 `daily_focus.national_id` 的完整資料、圖與網頁預覽，獨立核對來源、缺漏和重大問題，在 `reviews/YYYY-MM-DD.md` 記錄結論和可重現證據；不自行換號。為保持獨立性，審核任務只寫 `reviews/`，不直接修改 progress、guides 或圖片；次日建設者讀回審核報告並核實後，才同步更新 `daily_focus.review_status` 和是否達到完成門檻。
4. 三者每次回報**目前全國圖鑑編號、是否完整完成、未完成項目**、實際保存的 GitHub 連結與阻礙。若當日已完成，當日後續任務只能驗證/交接同一隻或結束，不能開始下一編號。

## 資料與寫入規則
- `data/guides.json` 結構 `{schema_version, updated_at, guides:[]}`；每項含 `key`、`national_id`、`game`、`topic`、`content`、`sources`、`checked_at`、`status`。唯一鍵 `<id>:<game>:<topic>`；依 key 更新，不新增重複。
- 記錄可靠來源 URL、來源類型、訪問日期、遊戲版本、GO PvE/PvP 或主系列玩法及查核狀態；以官方公告、官方支援和可核實的社群資料交叉比對。資訊有爭議則 `needs_review`，未審攻略維持 `draft`，不得虛構地點、招式、目前活動或排名。
- `data/pokemon.json` 及 `.github/workflows/` 由 GitHub Actions 專管，本流程不得修改。Actions 基本資料更新不等於某隻完整通過上述門檻。
- 每次寫入前讀最新檔案與 SHA，只改本輪必要資料、保留 queue/image_queue/history/blockers 和他人提交，寫後讀回核對；衝突須重新讀取合併，不覆蓋並行變更。
- 圖片須記錄原創來源、實際生成狀態及角色使用/展示權利；未通過審核不得冒用官方圖像或擅自公開展示。不付費、不繞過網站登入、驗證或限制。
- 若 GitHub、瀏覽器或額度受阻，保留同一焦點與具體缺漏，留到隔天繼續；沒有可用 Work 雲端環境時如實回報，不能聲稱已在該環境運作。排程可能延遲或失敗，不保證 24/7 運作。

## 單次批准、風險分級與單項發布（2026-11-25 共通規則）
- 同一圖片或獨立功能，以固定檔案路徑／SHA 或程式版本記錄一次可追溯決定。使用者或獨立品質審核 AI 任一方的專案內部品質／使用批准即可沿用；素材或功能有實質變更或新問題才重審。#001 現有圖片已有使用者的品質及私人專案用途批准，不重複索取。內部批准不等於第三方授權。
- 每個決定分別記錄：風險等級與實際依據、批准人／日期／範圍、第三方權利依據、GitHub／生成平台／網站與直接素材網址的可見性、必要技術測試及單項發布狀態。共通設定有證據時可重用；設定、用途、條款或素材來源實質改變才重查。GitHub 曾為 public，不得假定圖片儲存私人；Cloudflare Access 的登入頁不證明所有直連來源或允許身份已核實。
- 低風險：適用授權、原創權利或其他充分使用依據及條款通過；有條件風險：具體個人非營利使用依據、剩餘不確定性與限制範圍有記錄，且私人環境已證實；高風險：有具體適用禁止或侵權疑慮、公開暴露未核實或缺乏足夠使用依據，只暫緩相關素材。不能以泛稱法律不確定性單獨否決，也不能把專案批准說成權利人授權或以無人發現為依據。
- 視覺化任務對已滿足單項批准、權利、私人保護和必要測試的功能，可依使用者授權整合 main 並驗證正式私人網站；不需等整隻圖鑑完成或第二次品質批准。建設者只同步進度與交接，不自行批准素材權利或部署。單項發布、候選圖片及全角色八項完成門檻分別記錄；待審攻略不可冒稱已核實。

## 審核缺漏的接續方式
- 每次以當前 `daily_focus.national_id` 對照最新 `reviews/` 指明的既有攻略 key 與最新 `data/guides.json`。先修仍未解決的原 key，不以新增另一篇代替；新版本已可證實解決的項目略過，不讓舊報告形成每日重複待辦。
- 未查實的欄位在原 key 記明特定缺少的證據、來源分歧與下一步；逐 key 記錄本輪變更和提交，交接給視覺化端時分清可用事實與待查內容。此規則依焦點動態適用，不固定篇數或日期；保持建設、生圖、審核的原有寫入權限。
